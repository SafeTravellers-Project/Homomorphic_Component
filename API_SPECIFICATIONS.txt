  SAFETravellers HE Web Service — API Specification
  Version 3.0
================================================================================

OVERVIEW
--------
The SAFETravellers service exposes a RESTful HTTP API built with FastAPI
(Python). All data is exchanged in JSON (application/json) except for
biometric file uploads which use multipart/form-data.

The API wraps four Homomorphic Encryption (HE) binaries:
  HESysInit  — initialises FHE keys and system parameters
  Register   — encrypts and stores biometric templates in the country DB
  EncBio     — encrypts test biometrics at the E-Gate
  Verify     — performs encrypted biometric comparison

SESSION MODEL (read this first)
--------------------------------
All HE operations use a three-step session pattern to avoid long-held HTTP
connections and to allow dashboard polling of progress:

  STEP 1 — Create session
    POST /api/v1/sessions/<operation>
    Returns immediately with a session_id and URLs. The HE binary starts in
    the background. HTTP timeout is irrelevant.

  STEP 2 — Poll session status
    GET /api/v1/sessions/{session_id}
    Call this repeatedly (every 10–30 s) to track progress.

  STEP 3a — Retrieve result on COMPLETED
    GET /api/v1/sessions/{session_id}/result
    Returns the full operation result.

  STEP 3b — Handle failure on FAILED
    GET /api/v1/sessions/{session_id}/result
    Returns HTTP 422 with the error detail (raise condition for the client).

Session status lifecycle:
  PENDING   → session created, binary not yet started
  STARTED   → HE binary is executing
  COMPLETED → operation succeeded; result is available
  FAILED    → operation failed; error detail is available

Base URL:
  http://<host>:8080          (direct, without TLS)
  https://<your-domain>       (recommended for production, via Nginx)

Interactive API documentation (auto-generated by FastAPI):
  http://<host>:8080/docs     Swagger UI — try endpoints in browser
  http://<host>:8080/redoc    ReDoc — printable reference

--------------------------------------------------------------------------------
AUTHENTICATION
--------------------------------------------------------------------------------

All endpoints except GET /health require an API key in the request header:

  Header name : X-Api-Key
  Value       : the secret configured in SAFE_API_KEY on the server

Example:
  X-Api-Key: your-long-random-secret

If the key is missing or wrong:
  HTTP 401  {"detail": "Invalid API key"}

--------------------------------------------------------------------------------
COMMON RESPONSE CODES
--------------------------------------------------------------------------------

  200 OK           — request accepted or data returned successfully
  400 Bad Request  — invalid input (missing files, bad folder name, etc.)
  401 Unauthorized — missing or wrong API key
  404 Not Found    — session_id does not exist
  409 Conflict     — result requested but session not yet COMPLETED
  422 Unprocessable — result requested but session is FAILED (raise condition)
  500 Internal Server Error — unexpected server error

SESSION OBJECT SCHEMA
--------------------------------------------------------------------------------

Session status response (returned by GET /api/v1/sessions/{session_id}):

  {
    "session_id":  "3f2a1b4c-...",          string — unique session identifier (UUID)
    "operation":   "verify",               string — init | register | encrypt-bio | verify
    "status":      "STARTED",              string — PENDING | STARTED | COMPLETED | FAILED
    "created_at":  "2026-04-20T10:00:00Z", string — ISO 8601 UTC, when session was created
    "updated_at":  "2026-04-20T10:02:14Z", string — ISO 8601 UTC, last status change
    "error":       null                    string | null — populated when status = FAILED
  }

Session creation response (returned by POST /api/v1/sessions/<operation>):

  {
    "session_id":  "3f2a1b4c-...",
    "operation":   "verify",
    "status":      "PENDING",
    "created_at":  "2026-04-20T10:00:00Z",
    "poll_url":    "/api/v1/sessions/3f2a1b4c-...",
    "result_url":  "/api/v1/sessions/3f2a1b4c-.../result"
  }

Session result response (returned by GET /api/v1/sessions/{session_id}/result):

  {
    "session_id":    "3f2a1b4c-...",
    "operation":     "verify",
    "status":        "COMPLETED",
    "created_at":    "2026-04-20T10:00:00Z",
    "completed_at":  "2026-04-20T10:12:44Z",
    "result":        { <operation-specific result — see each endpoint below> }
  }

--------------------------------------------------------------------------------
ENDPOINT 1 — Health Check  (dashboard manager polling)
--------------------------------------------------------------------------------

  Method  : GET
  Path    : /health
  Auth    : NOT required

  Description:
    Returns the service liveness status and the count of currently running
    sessions. The SAFETravellers dashboard calls this periodically (every ~30 s)
    as its manager polling mechanism.

  Response (200 OK):
    {
      "status":          "ok",
      "service":         "SAFETravellers API",
      "active_sessions": 1
    }

  "active_sessions" is the count of sessions currently in STARTED state.

  Example:
    curl http://localhost:8080/health

--------------------------------------------------------------------------------
ENDPOINT 2 — Poll Session Status
--------------------------------------------------------------------------------

  Method  : GET
  Path    : /api/v1/sessions/{session_id}
  Auth    : required

  Description:
    Returns the current status of a session. Poll this after any POST operation
    until status = COMPLETED or FAILED.
    Recommended polling interval: every 10–30 seconds.

  Response (200 OK):
    <SessionStatus object — see schema above>

  Error (404):
    {"detail": "Session not found: <session_id>"}

  Example:
    curl http://localhost:8080/api/v1/sessions/3f2a1b4c-... \
      -H "X-Api-Key: your-long-random-secret"

--------------------------------------------------------------------------------
ENDPOINT 3 — Retrieve Session Result
--------------------------------------------------------------------------------

  Method  : GET
  Path    : /api/v1/sessions/{session_id}/result
  Auth    : required

  Description:
    Returns the full operation result when status = COMPLETED.
    Returns HTTP 422 (raise condition) when status = FAILED.
    Returns HTTP 409 if the session is still PENDING or STARTED.

    Only call this endpoint after polling confirms status = COMPLETED or FAILED.

  Response (200 OK — COMPLETED):
    <SessionResult object — see schema above>
    The "result" field contains the operation-specific output (see each
    endpoint below for the exact shape).

  Response (422 — FAILED — raise condition):
    {
      "detail": {
        "session_id": "3f2a1b4c-...",
        "operation":  "verify",
        "status":     "FAILED",
        "error":      "<reason the HE binary failed>"
      }
    }

  Response (409 — not yet finished):
    {"detail": "Session is not yet completed. Current status: STARTED"}

  Example:
    curl http://localhost:8080/api/v1/sessions/3f2a1b4c-.../result \
      -H "X-Api-Key: your-long-random-secret"

--------------------------------------------------------------------------------
ENDPOINT 4 — List All Sessions

  Method  : GET
  Path    : /api/v1/sessions
  Auth    : required

  Description:

  Response (200 OK):

  Example:
    curl http://localhost:8080/api/v1/sessions \
      -H "X-Api-Key: your-long-random-secret"

--------------------------------------------------------------------------------
ENDPOINT 5 — Create Init Session
--------------------------------------------------------------------------------

  Method  : POST
  Path    : /api/v1/sessions/init
  Auth    : required

  Description:
    Starts HESysInit in the background to generate or regenerate all FHE keys
    and system parameters. Typical duration: several minutes.

    WARNING: Calling this invalidates all previously encrypted biometric data.
    Only use when a full re-enrolment is planned.

  Request body: none (no Content-Type required)

  Response (200 OK — session created):
    <SessionCreated object>

  Result shape (inside SessionResult.result when COMPLETED):
    {
      "ok":        true,
      "command":   ["./HESysInit"],
      "exit_code": 0,
      "stdout":    "<HESysInit output>",
      "stderr":    ""
    }

  Example:
    # Step 1 — create session
    curl -X POST  https://platform.safetravellers.rid-intrasoft.eu/hews/api/v1/sessions/init \
      -H "X-Api-Key: your-long-random-secret"

    # Step 2 — poll (replace <session_id> with value from Step 1 response)
    curl  https://platform.safetravellers.rid-intrasoft.eu/hews/api/v1/sessions/<session_id> \
      -H "X-Api-Key: your-long-random-secret"

    # Step 3 — get result once COMPLETED
    curl https://platform.safetravellers.rid-intrasoft.eu/hews/api/v1/sessions/<session_id>/result \
      -H "X-Api-Key: your-long-random-secret"

--------------------------------------------------------------------------------
ENDPOINT 6 — Create Register Session
--------------------------------------------------------------------------------

  Method       : POST
  Path         : /api/v1/sessions/register
  Auth         : required
  Content-Type : multipart/form-data

  Description:
    Uploads raw biometric templates, then asynchronously encrypts and stores
    them in the country database. The "encrypted_output_dir" in the result
    must be stored in your database — it is needed for Verify.

  Form fields:
    files          (required, one or more)  Raw biometric template files.
    output_bucket  (optional, default: "default")
                   Traveller identifier / bucket label.
                   Allowed: letters, digits, dots, hyphens, underscores.

  Response (200 OK — session created):
    <SessionCreated object>

  Result shape when COMPLETED:
    {
      "ok":                   true,
      "uploaded_files":       #number of files in the folder,
      "encrypted_output_dir": "/app/data/CountryDB/Reg_Biometrics_Enc/<bucket>/<timestamp>"
    }

  Errors (immediate, before session is created):
    400 — {"detail": "No valid files uploaded"}
    400 — {"detail": "Invalid folder name"}

  Example:
    # Step 1 — create session
    curl -X POST https://platform.safetravellers.rid-intrasoft.eu/hews/api/v1/sessions/register \
      -H "X-Api-Key: your-long-random-secret" \
      -H "Content-Type: application/json" \
      -d '{
          "input_folder": "data/Traveller/Reg_Bio",
          "output_bucket": "e2e_party_reg"
          }'

    # Step 2 — poll
    curl https://platform.safetravellers.rid-intrasoft.eu/hews/api/v1/sessions/<session_id> \
      -H "X-Api-Key: your-long-random-secret"

    # Step 3 — get result (save encrypted_output_dir for later Verify call)
    curl https://platform.safetravellers.rid-intrasoft.eu/hews/api/v1/sessions/<session_id>/result \
      -H "X-Api-Key: your-long-random-secret"

    curl https://platform.safetravellers.rid-intrasoft.eu/hews/api/v1/sessions/<session_id> \

--------------------------------------------------------------------------------
ENDPOINT 8 — Create Verify Session
--------------------------------------------------------------------------------

  Method       : POST
  Path         : /api/v1/sessions/verify
  Auth         : required
  Content-Type : application/json

  Description:
    Starts an asynchronous HE comparison between a live encrypted biometric
    (from encrypt-bio) and a stored encrypted registration (from register).
    No raw biometric data is ever decrypted. This is the most compute-intensive
    operation — typical duration is several minutes to up to 30 minutes.

  Request body (JSON):
    {
      "threshold":               2000,
      "test_encrypted_folder":   "<encrypted_output_dir from encrypt-bio result>",
      "stored_encrypted_folder": "<encrypted_output_dir from register result>"
    }

  Fields:
    threshold               (integer, required)
                            HE comparison decision threshold. Typical value: 2000.

    test_encrypted_folder   (string, required)
                            Path returned by a previous encrypt-bio session result.
                            Absolute or relative to /app/. Must stay inside /app/.

    stored_encrypted_folder (string, required)
                            Path returned by a previous register session result.
                            Same path restrictions.

  Response (200 OK — session created):
    <SessionCreated object>

  Result shape when COMPLETED:
    {
      "ok":                 true,
      "verify_result_line": "|| MATCH || score: 1842 || threshold: 2000 ||",
      "stdout":             "<full Verify output>",
      "stderr":             ""
    }

    Parse "verify_result_line" for the MATCH / NO MATCH decision and score.

  Errors (immediate):
    400 — {"detail": "Test folder not found: ..."}
    400 — {"detail": "Stored folder not found: ..."}
    400 — {"detail": "Path must stay inside project root"}

  Example:
    # Step 1 — create session
    curl -X POST https://platform.safetravellers.rid-intrasoft.eu/hews/api/v1/sessions/verify \
      -H "Content-Type: application/json" \
      -H "X-Api-Key: your-long-random-secret" \
      -d '{
        "threshold": 7000,
        "test_encrypted_folder":
          "/app/data/E-Gate/Test_Bio_Enc/gate_B1/20260420_110000/live_scan_enc",
        "stored_encrypted_folder":
          "/app/data/CountryDB/Reg_Biometrics_Enc/traveller_A42/20260420_100000/template1_enc"
      }'

    # Step 2 — poll every 30 s
    curl https://platform.safetravellers.rid-intrasoft.eu/hews/api/v1/sessions/<session_id> \
      -H "X-Api-Key: your-long-random-secret"

    # Step 3a — get result when COMPLETED
    curl https://platform.safetravellers.rid-intrasoft.eu/hews/api/v1/sessions/<session_id>/result \
      -H "X-Api-Key: your-long-random-secret"

    # Step 3b — handle FAILED (HTTP 422 is returned — raise condition)
    # Your client should detect status=FAILED from Step 2 polling before
    # calling /result, and handle the 422 response accordingly.

--------------------------------------------------------------------------------
TYPICAL INTEGRATION WORKFLOW
--------------------------------------------------------------------------------

  ENROLMENT (once per traveller):
  --------------------------------
  1.  POST /api/v1/sessions/register     → save session_id
  2.  Poll GET /api/v1/sessions/{id}     → wait for COMPLETED or FAILED
  3.  If FAILED: GET /api/v1/sessions/{id}/result → raises 422 with error
  4.  If COMPLETED: GET /api/v1/sessions/{id}/result
      → save result.encrypted_output_dir in your database for this traveller

  BORDER CROSSING (each E-Gate passage):
  ----------------------------------------
  5.  POST /api/v1/sessions/encrypt-bio  → save session_id
  6.  Poll until COMPLETED; GET result   → note encrypted_output_dir
  7.  POST /api/v1/sessions/verify
        threshold, test=step6 path, stored=step4 path  → save session_id
  8.  Poll until COMPLETED or FAILED
  9.  If COMPLETED: GET result → read verify_result_line → open/block gate
  10. If FAILED:    GET result → HTTP 422 → raise alert / manual review

  DASHBOARD MONITORING:
  ----------------------
  - GET /health every 30 s → active_sessions count for real-time workload display
  - GET /api/v1/sessions   → full session history/log panel

  MAINTENANCE:
  ------------
  - POST /api/v1/sessions/init → only when full key rotation is required.

NOTES FOR THIRD-PARTY DEVELOPERS
--------------------------------------------------------------------------------

1. Protocol
   REST over HTTP/1.1. JSON bodies except file uploads (multipart/form-data).
   No WebSocket, gRPC, or SOAP.

2. Client timeout
   Because all operations return immediately, there is no need to set long HTTP
   timeouts on the POST calls. A standard 30-second timeout is sufficient.
   The HE work happens asynchronously regardless of how long the client waits.

3. Raise condition on FAILED
   When status = FAILED, calling GET /result returns HTTP 422. Clients should
   handle this as an application-level error: log the error detail, alert an
   operator, and do not proceed with the gate decision.

4. Session persistence
   Sessions live in memory and do NOT survive a container restart. Always
   save the "encrypted_output_dir" paths from completed sessions to your own
   database. Do not rely on session_ids after a restart.

5. Encrypted data persistence
   The "encrypted_output_dir" directories ARE preserved across container
   restarts (stored on Docker named volumes). They are only invalidated by
   calling /sessions/init (key regeneration).

6. No raw biometric data retained
   Raw files uploaded to /register and /encrypt-bio are deleted from the
   server immediately after the background task copies them to a temp folder.

7. Interactive documentation
   http://<host>:8080/docs    Swagger UI (try requests live)
   http://<host>:8080/redoc   ReDoc (printable)
